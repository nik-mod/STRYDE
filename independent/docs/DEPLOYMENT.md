# Independent hosting preparation

No domain was purchased and nothing was deployed. Docker files and Compose are preparation; Docker is unavailable on this machine, so container builds, proxy behavior and certificate issuance have not been executed here. Native Next and Medusa production builds are validated separately.

The proposed single-host stack is Next → private Medusa → PostgreSQL 18, with Redis for durable events/workflow execution, PostgreSQL advisory locking, persistent upload storage, nginx shared IP rate limits and Caddy for HTTPS. PostgreSQL and Redis have no public port. Medusa's port is bound only to the server's loopback interface; use an SSH tunnel/VPN and an HTTPS admin hostname. The public site only proxies a constrained same-origin cart/checkout interface. The admin API uses Medusa authentication; never send admin credentials to the storefront. Customer accounts are deliberately deferred; guest order creation does not require account passwords.

1. Select hosting and domain; arrange backups and a private administrator access path. Create a clean production database. Do not copy the development database or seed fixtures there.
2. Copy `deploy/backend.env.example` and `deploy/storefront.env.example` to the corresponding `.env` filenames; generate independent random secrets. These files are ignored by Git and excluded from image build context. Set domain and database password in a private Compose environment. Do not use the placeholder values. Configure the real sales region, currency, approved catalog, tax and shipping in Medusa Admin. Create the production publishable key and set it only in the server environment. The storefront's cart cookie secret and Medusa secrets are different.
3. Build containers in staging. The backend build uses disposable build-only configuration and does not migrate a database during image construction. Apply `medusa db:migrate` as a one-off release job using the production backend image/environment before starting application workers. Medusa's pinned migrations cover products, pricing, inventory, carts, orders and locks. Rehearse migrations against a restored backup first.
4. Point the chosen domain's A record at the host's IPv4 address. Add AAAA only if IPv6 actually routes to it. Add the chosen `www` alias and canonical redirect if desired. Remove conflicting old hosting records. Allow TCP 80/443 for Caddy's certificate challenge and HTTPS; keep database, Redis and administration private. Configure the actual `SITE_URL` and HTTPS CORS allowlists; no domain is assumed in source.
5. Confirm TLS and renewal, secure/HttpOnly/SameSite bag cookies, headers, origin validation, nginx limits, health endpoint and private admin access in staging. Do not forward unauthenticated client headers into trusted proxy headers. Backend config requires strong secrets, HTTPS CORS and Redis in production. A local Docker network may use unencrypted PostgreSQL; a remote database must use verified TLS (`DATABASE_SSL=true`) and restricted network access.
6. Configure durable public product image hosting (owned object storage or a properly routed upload origin); verify ownership and URLs before catalog import. Existing creative assets/fonts/models are local, version controlled and cached. WebP photography and GLBs are reused without quality changes. Product prices, stock, cart, checkout and API responses use `no-store`. No remote image optimizer allowlist is guessed; configure exact owned media domains before using Next image optimization. Static assets use a one-hour revalidation cache until their filenames are content versioned.
7. Complete the merchant/payment/legal decisions in `PAYMENTS.md`. Implement and sandbox-test the selected hosted bank adapter and authenticated callbacks. Configure transaction email with a real sender and retry/delivery monitoring, then replace policy placeholders with approved documents and contact details. Current order events produce structured logs only, not email.
8. Resolve remaining dependency advisories, rerun audits/builds/browser checks, test backup recovery and obtain deployment authorization. This code cannot take live payments as it stands. Passing a build is not launch approval.

## Operations

Use `/api/health` for storefront-to-backend readiness and Medusa `/health` privately. Next logs structured commerce failure events without credentials or customer address/email payloads. Medusa records orders persistently. Caddy access logs are JSON on stdout. Send infrastructure logs to your owned log collector with access controls/retention; alert on health failures, elevated 5xx, failed order workflows and future bank callback/reconciliation failures. No monitoring SaaS credentials or DSN were fabricated. A durable transactional email provider is still required; the present subscriber logs `email_provider_not_configured`.

Schedule encrypted PostgreSQL logical backups daily using `pg_dump --format=custom`, with credentials supplied via a secret file/secret manager, never command history. Copy to separately controlled storage; keep a documented retention schedule (for example 7 daily/4 weekly) and consider WAL archiving for a defined recovery point objective. Back up uploads, environment configuration (encrypted), Redis AOF and certificate volumes separately. Do not put customer backups into Git. Restore into a new database with `pg_restore`, validate row counts/orders/stock, run matching application migrations, test checkout in a sandbox, then switch traffic. Rehearse this before launch and after major migrations. A successful dump alone is not a recovery test.

## Security scope

Next accepts no client prices/totals; Medusa validates inventory and calculates tax/shipping/totals. Cart IDs are in expiring HMAC-signed HttpOnly cookies, never a shared in-memory mock cart. Writes require the configured exact Origin, JSON and strict bounded schemas (16 KiB maximum). Line mutations check membership in the current bag. Rate limits are per-process in development and per-IP at the prepared shared production proxy. Live payment/session completion is blocked in Medusa even if callers bypass Next. Private Admin and strong authentication remain essential.

The CSP allows inline scripts/styles required by Next hydration and the preserved GSAP scene, and blob connections required for embedded GLB textures. It blocks objects, framing and foreign form submissions. It is not a strict nonce-only policy. Dynamic commerce content is rendered through React text escaping; trusted HTML fragments come only from local version-controlled design files. Never place untrusted merchant/customer HTML into those fragments. Any future rich text must be sanitized separately.
